## 2. Twilio Platform Integrations

### 2.1 Twilio Flex (Agent Desktop Framework)

**Current Role:** Flex IS the agent desktop. The plugin-hrm-form is a Flex Plugin that extends the Flex UI.

**For MAUI Rebuild:** Flex will no longer be the UI framework. Instead, the MAUI app will directly interact with Twilio APIs.

**APIs to consume directly:**
- Flex Webchat API (v2) — for webchannel creation
- Flex Configuration API — for feature flags and service config
- Flex Token generation — for agent authentication

**SDK:** [`twilio-flex-token-validator`](https://www.npmjs.com/package/twilio-flex-token-validator)

### 2.2 Twilio Conversations SDK

**Purpose:** Real-time chat messaging between agents and callers.

**Integration Points:**
- Initialize client with JWT token
- Join/leave conversations
- Send/receive messages (text + media)
- Typing indicators
- Participant management
- Conversation state changes (active, closed)
- Message read receipts

**For MAUI:** Use [Twilio Conversations SDK for .NET](https://www.twilio.com/docs/conversations) or REST API equivalent.

### 2.3 Twilio TaskRouter

**Purpose:** Distribute incoming tasks (calls, chats) to available agents based on skills and availability.

**Integration Points:**
- Worker registration and status management
- Task acceptance, rejection, wrapping, completion
- Transfer operations (warm, cold)
- Queue management
- Skill-based routing

**Key Events:**
- `reservationCreated` — new task assigned
- `reservationAccepted` — agent accepts
- `reservationWrapup` — task in wrapup phase
- `reservationCompleted` — task finished
- `reservationTimeout` — agent didn't respond

### 2.4 Twilio Voice

**Purpose:** Voice calling (PSTN and VoIP).

**Integration Points:**
- Accept/reject incoming calls
- Conference management (add/remove/mute/hold participants)
- Call recording lookup
- Conversation duration tracking
- Warm/cold transfer

### 2.5 Twilio Sync

**Purpose:** Real-time data synchronization (queue counts, worker status).

**Integration Points:**
- Subscribe to Sync documents/lists
- Real-time queue status updates
- Worker activity state sync

## 3. AWS Integrations

### 3.1 AWS Lambda

**Purpose:** Serverless backend for Twilio webhook handling and API orchestration.

**Architecture:**
- ALB → Lambda (account-scoped handler with 60+ routes)
- Direct Lambda invocation for satellite functions

**For MAUI:** Lambda functions can remain as-is. The MAUI app calls them via HTTP (same REST API).

### 3.2 AWS S3

**Purpose:** File storage for recordings, transcripts, documents, and static configuration.

**Usage:**
- Voice recordings (S3StoredRecording)
- Conversation transcripts (S3StoredTranscript)
- Webhook routing maps (line-webhook-map.json, modica-webhook-map.json)
- Webchat widget assets (compiled JS/CSS)
- Terraform state

**For MAUI:** Access via signed URLs generated by the Lambda/HRM API. No direct S3 access from MAUI.

### 3.3 AWS SSM Parameter Store

**Purpose:** Secrets and configuration management.

**Parameter Patterns:**
- `/global/{param}` — Global parameters
- `/{environment}/{helpline}/{param}` — Per-helpline secrets

**Stored Values:**
- Twilio Account SID / Auth Token
- API keys and secrets
- reCAPTCHA secrets
- Datadog credentials
- HRM API URLs

**For MAUI:** Not accessed directly. Lambda functions read SSM parameters.

## 4. Social Media Channel Integrations

### 4.1 Instagram

**Flow:**
```
Instagram User → Facebook Graph API → Instagram Webhook Lambda
  → HMAC-SHA1 signature verification (X-Hub-Signature header)
  → Parse message → Forward to Twilio Conversations
  → Agent responds in Flex/MAUI → Lambda (flexToInstagram) → Instagram API → User
```

**Auth:** Facebook App Secret for webhook HMAC-SHA1 verification.
**Lambda Routes:**
- `customChannels/instagram/instagramToFlex` — No auth (public webhook)
- `customChannels/instagram/flexToInstagram` — Twilio webhook auth

### 4.2 Facebook Messenger

**OAuth Token Exchange (3-step flow via facebookSignin/facebookCallback lambdas):**
```
Step 1: Agent initiates Facebook Page connection
  → Redirect to Facebook OAuth with app_id, redirect_uri, scope
  
Step 2: Facebook callback with authorization code
  → Lambda exchanges code for short-lived user token
    POST https://graph.facebook.com/v12.0/oauth/access_token
    
Step 3: Exchange short-lived token for long-lived page token
  → GET https://graph.facebook.com/v12.0/me/accounts?access_token={user_token}
  → Returns page access tokens for subscribed pages
  → Store page token in SSM Parameter Store
```

**Integration:** Via Twilio's native Facebook Messenger channel once page token is configured.

### 4.3 Telegram

**Flow:**
```
Telegram User → Telegram Bot API → telegramToFlex handler (no auth)
  → S3 webhook map lookup (telegram-webhook-map.json)
  → Parse message → Forward to Twilio Conversations
  → Agent responds → flexToTelegram handler (webhook auth) → Telegram Bot API → User
```

### 4.4 LINE

**Flow:**
```
LINE User → LINE Messaging API → lineToFlex handler (no auth)
  → S3 webhook map lookup (line-webhook-map.json)  
  → LINE signature verification (HMAC-SHA256 with Unicode emoji normalization)
  → Parse message → Forward to Twilio Conversations
  → Agent responds → flexToLine handler (webhook auth) → LINE Messaging API → User
```

**HMAC Verification Details:**
- Algorithm: HMAC-SHA256 (not SHA1 like Instagram)
- Special handling: Unicode emoji normalization before hashing
- Signature header: `x-line-signature` (preserved and forwarded)
- Timing-safe comparison to prevent timing attacks

**Setup:** `lineSetup` Lambda configures webhook mapping in S3:
1. Get bot info from LINE API
2. Create S3 mapping (LINE Channel ID → Twilio account)
3. Store channel credentials in SSM

### 4.5 Modica

**Flow:**
```
Modica SMS → Modica Webhook → modicaToFlex handler (no auth)
  → S3 webhook map lookup (modica-webhook-map.json)
  → Parse message → Forward to Twilio Conversations
  → Agent responds → flexToModica handler (webhook auth) → Modica API → User
```

### 4.6 WhatsApp

**Integration:** Via Twilio's native WhatsApp Business API channel. No custom webhook needed.

### Custom Channel Architecture

All custom channels use a generic abstraction:

```typescript
type AseloCustomChannel = {
  identity: string;            // Channel-specific user identifier
  studioFlowSid: string;      // Twilio Studio flow for routing
  createConversationOnChannelMessage: boolean;
}
```

## 5. Analytics & Monitoring Integrations

### 5.1 FullStory

**Purpose:** Session recording and analytics for agent desktop.

**Feature Flag:** `enable_fullstory_monitoring`

**Initialization:**
```
FullStory.init({
  orgId: from secret.ts module,
  devMode: ENABLE_MONITORING !== 'true'  // dev mode in non-production
})
```

**User & Page Context:**
```
setUserVars({
  helplineCode, accountSid, displayName, email, workerSid, environment
})
setVars('page', {
  flexVersion, helplineCode, pluginUrl, pluginVersion
})
```

**Event Recording API:**
```
recordEvent(eventName, properties)            // Generic event tracking
recordFormValidationError(formName, field, error) // Form validation failures
recordBackendError(endpoint, statusCode, error)  // API error tracking
recordingErrorHandler HOC                     // Wraps page components for automatic error capture
```

**For MAUI:** FullStory has a mobile SDK. Alternatively, use App Center Analytics or a different analytics solution. Event recording API patterns should be preserved.

### 5.2 Datadog

**Purpose:** Error monitoring, alerting, and infrastructure metrics.

**Integration — TwilioErrorReporter Lambda:**
- Receives Twilio error events via CloudWatch/EventBridge
- **PII Filtering:** Strips sensitive data before forwarding:
  - Filters error payloads to remove phone numbers, personal info (customerAddress, customerName, from, caller)
  - Only forwards metadata: error code, account SID, timestamp
- **Error Filtering:** Configurable filtering by:
  - Account SID (only forward errors from specific accounts)
  - Error code (suppress known non-actionable errors by account+code)
- **Dual Output:** Sends filtered events to:
  1. Datadog Event API (primary)
  2. SNS topic (secondary — for cross-account notification)
- Custom metrics and infrastructure monitoring

**Terraform Datadog Module (terraform-modules/datadog/v1):**
- Studio flow execution metrics
- Threshold-based alerting (configurable per helpline)
- Custom monitoring schedules
- Integration with Datadog API

**For MAUI:** Use Datadog Mobile SDK or App Center.

### 5.3 Twilio Insights

**Purpose:** Analytics/reporting on contact and case data.

**Feature Flag:** `enable_save_insights`

**Integration:**
- Push data via `InsightsService` after contact save
- One-to-one mapping (contact fields → Insights attributes)
- One-to-many mapping (categories → Insights attributes)
- Post-survey data

**Purpose:** Bot prevention on public-facing webchat form.

**Feature Flag:** `enable_recaptcha` (webchat config)

**Flow:**
```
User fills form → reCAPTCHA challenge → Token generated
  → POST /recaptchaValidation → Lambda verifies with Google
  → Success → Proceed with webchat init
```

## 8. IWF (Internet Watch Foundation) Integration

**Purpose:** Report child sexual abuse material (CSAM) to IWF.

**Feature Flag:** `use_twilio_lambda_for_iwf_reporting`

**Integration — Two Report Types:**

Counsellor-generated report (`reportToIWF`):
```
Fields sent:
  Reported_URL: form.webAddress
  Reporter_Description: form.description
  Reporter_Anonymous: "Y" or "N" (from form.anonymous === 'anonymous')
  Reporter_First_Name: form.firstName
  Reporter_Last_Name: form.lastName
  Reporter_Email_ID: form.email
```

Self/child-generated report (`selfReportToIWF`):
```
Fields sent:
  user_age_range: form.childAge
  case_number: caseNumber (from linked case)
```

**Lambda routes:**
- `integrations/iwf/reportToIWF` — agent token auth
- `integrations/iwf/selfReportToIWF` — agent token auth

## 9. Amazon Lex Integration

**Purpose:** Chatbot for initial conversation handling before agent handoff and post-survey data collection.

**Infrastructure:** Configured via Terraform modules:

### Lex v1 (`terraform-modules/lex/v1`)
```
Resources:
  aws_lex_slot_type → Custom slot types for conversation data
  aws_lex_intent → Intent definitions with:
    ├── Sample utterances (trigger phrases)
    ├── Slot definitions (data capture)
    └── Fulfillment activity (dialog or Lambda)
```

### Lex v2 (`terraform-modules/lex/v2`)
```
Resources:
  Bot locales (multi-language support)
  Slot priorities (conversation flow ordering)
  Intent recognition models
```

**Bot Channel Capture Flow:**
```
Webchat user → Pre-engagement form → Twilio Studio Flow
  → captureChannelWithBot Lambda:
     ├── Creates CapturedChannelAttributes:
     │   { userId, environment, helplineCode, botLanguage, botSuffix,
     │     controlTaskSid, releaseType, studioFlowSid, channelType,
     │     isConversation, chatbotCallbackWebhookSid }
     ├── releaseType: 'triggerStudioFlow' → agent handoff after bot
     └── releaseType: 'postSurveyComplete' → end after survey
  → Lex chatbot handles initial interaction
  → chatbotCallback → Bot complete:
     ├── If triggerStudioFlow: initiate Studio flow → TaskRouter → Agent
     └── If postSurveyComplete: close conversation
  → chatbotCallbackCleanup → Clean up bot state
```

## 9B. HRM Internal API Integration

**Purpose:** Lambda functions communicate with the HRM backend using a dedicated internal API.

**URL Pattern:** `/internal/${apiVersion}/accounts/${hrmAccountId}/${path}`

**Authentication:** Basic Auth with a static API key stored in SSM (rotated independently of Flex tokens).

**Retry Policy:** 3 attempts on failure.

**Used by:**
- TaskRouter event handlers (RESERVATION_ACCEPTED → create contact)
- Chatbot callback processing (update contact with bot interaction data)
- Post-survey handling (save survey responses)
- Profile flag lookup for routing decisions

**Security:** Timing-safe HMAC comparisons used throughout custom channel webhook verification to prevent timing attacks.

## 11. SaferNet Dual-Write Integration (Brazil)

**Purpose:** Synchronize contact data to SaferNet backend for Brazilian helplines.

**Feature Flag:** `enable_dual_write`

**Flow:**
```
Contact saved to HRM API (primary)
  ↓
Call ServerlessService.saveContactToExternalBackend(contact)
  ├── On success: dual-write complete
  └── On failure:
      ├── Create SyncService document with contact data
      ├── Sync document acts as retry queue
      └── Background process retries delivery
```

**For MAUI:** Same pattern — save to HRM first, then POST to SaferNet endpoint. Implement retry queue with SQLite or similar.

## 12. IP Geolocation Integration

**Purpose:** Detect user location for analytics and IP blocking (legacy webchat).

**Service:** ipfind.co API

**Webchat Flow:**
```
1. Legacy webchat loads → call ipfind.co API with user IP
2. Response includes country, city, region
3. Check IP against helpline-specific blocked IP JSON list
4. If blocked → show blocked message, prevent chat init
5. If allowed → proceed with pre-engagement form
```

**Lambda:** `ipLocationFinder` Lambda wraps ipfind.co calls for server-side geolocation.

## 13. Region Utilities

**Purpose:** Twilio has regional deployments; URLs and SDK configs vary by region.

**Four transform functions:**

| Function | Input | Output Example |
|----------|-------|----------------|
| `buildRegionalHost(region)` | `"prod"` → `""`, `"dev-us1"` → `".dev"`, `"stage-us1"` → `".stage"` | Host suffix for URLs |
| `parseRegionForConversations(region)` | `"prod"` → `"us1"`, `"dev"` → `"dev-us1"` | Conversations SDK region param |

**Used in:** Webchat backend URL construction, Conversations SDK initialization, EventBridge region config.
